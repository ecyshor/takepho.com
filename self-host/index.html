Run Takeout Photo on a NAS with Docker Compose

The Docker image is public at ghcr.io/ecyshor/takepho and runs on x86 (amd64) and 64-bit ARM (arm64) servers. It gives you the same app, and the same three apps, running on your NAS or home server, open in a browser on your network. Your scheduled Takeout exports can land in a folder on the NAS.

Takeout Photo runs on your own server with Docker Compose. One container serves the web UI and the API. Your photos stay on your machine: the app indexes the Takeout archives in place and never copies the originals.

What you get

  • The photos app: timeline, trips, map, AI curation of the best photos per trip (CLIP aesthetic scoring, runs locally on CPU or GPU).
  • The activities app: Strava, Komoot and Garmin Connect import, routes on a map, photo matching, stats.
  • The sync app: backs your Google Photos up to Proton Photos.
  • All local: your photos never leave the server. A plan is required to import your own Takeout (sign in at Settings → Account, see "Plans and licensing" below); the sample data is free. Turn apps on or off with the APPS variable (photos,activities,sync by default).

Requirements

  • Docker Engine + Compose v2.24+ on the server: Docker Desktop, or the Docker package of your NAS / home-server OS (Synology Container Manager, Unraid, TrueNAS SCALE, Portainer, ...).

  • CPU architecture: the published CPU image (ghcr.io/ecyshor/takepho) is multi-arch, linux/amd64 + linux/arm64, so Docker pulls the native build on x86 servers and on ARM machines such as Synology DS-series models with ARM CPUs and Raspberry Pi 4/5 with a 64-bit OS. The CUDA image (ghcr.io/ecyshor/takepho-cuda) is linux/amd64 only.

  • RAM: plan for at least 4 GB of free memory for the container (both amd64 and arm64), 8 GB if you have a large library and run AI curation on the CPU. Ingestion uses cpu_count - 2 parallel workers by default (INGEST_WORKERS).

  • Disk, in two parts:

    • The Takeout folder stays where it is and is mounted read-only. Its size is your Google Photos library including videos.
    • The data dir (/data) holds the databases, thumbnails and previews, gzip indexes, uploads and Drive downloads. From a real 34,000-photo / 249 GB library: about 400 KB per photo in a trip (400 px + 1600 px previews) and 35 KB per other photo, about 1.5 MB of index per GB of .tgz archives, about 5 KB of database per photo, plus each Drive archive's size (plus 2 GB free) in /data/downloads while it is ingested.
    • The models volume holds the CLIP weights: the aesthetic head ships in the image, the ViT-B/32 weights (about 578 MB) download on the first AI curation run.

Quick start

Make a folder on the server, download the two files this guide ships, and start:

mkdir ~/takepho && cd ~/takepho
          curl -fsSLO https://takepho.com/self-host/compose.yaml
          curl -fsSLO https://takepho.com/self-host/backend.env.example
          cp backend.env.example backend.env    # optional: adjust settings, see "Configuration"
          docker compose pull
          docker compose up -d

compose.yaml (the full file is shown below) pulls the public image ghcr.io/ecyshor/takepho:latest from GHCR (amd64 + arm64) and starts one container; backend.env.example is the commented example for backend.env (the file is optional). Compose variables such as TIMELINE_PORT go in a .env next to the compose file.

Then open http://<nas-host>:8080 (default host port 8080, change it with TIMELINE_PORT in that .env). http://<nas-host>:8080/health answers {"status": "healthy"}; the API docs are at /docs.

First import: without a plan you get Lite (free tier) — the photos timeline, read-only and limited to your 5 most recent holidays, plus a manual import of a local folder on the Takeout page (a newer export can be imported the same way, which rebuilds the library; you can also cancel/resume your own manual import jobs; everything else is refused with HTTP 402; the sample data is free). To unlock the full library, sign in and buy a plan first (Settings → Account, see "Plans and licensing" below). Then, on the Takeout page, in the Takeout source card pick a local folder (/takeout, the mounted Takeout dir), a Google Drive link, or a Google account, then press "Import now". The "How to get your Takeout" guide on that page walks through creating the export. Turn on "Watch for new exports" to import scheduled exports automatically (needs the yearly plan).

The compose file

The reference setup is compose.yaml, published with this guide at https://takepho.com/self-host/compose.yaml and shown in full below — a pull-only example (no build:). One service, app, from the image ghcr.io/ecyshor/takepho:latest (the image serves the backend + built UI in a single container: FastAPI serves the UI from / and the API under /api). Save the download as compose.yaml in your folder and start it (see Quick start):

# Takeout Photo - self-hosting on a NAS / home server (single container, pull-only)
          #
          # The published CPU image ghcr.io/ecyshor/takepho:latest is multi-arch
          # (linux/amd64 + linux/arm64), so it pulls natively on x86 and on ARM (64-bit)
          # servers: Synology DS-series with ARM CPUs, Raspberry Pi 4/5 with a 64-bit OS.
          # The CUDA image at the bottom is linux/amd64 only.
          #
          # Run: docker compose pull && docker compose up -d
          #   (from the app repository root, under this file's name:
          #    docker compose -f compose.nas.yaml pull && docker compose -f compose.nas.yaml up -d)
          # Open: http://<nas-host>:8080   (health: http://<nas-host>:8080/health, API docs: /docs)
          #
          # Configuration: set TIMELINE_DATA, TIMELINE_MODELS, TAKEOUT_DIR, TIMELINE_PORT
          # in the shell or in a .env file next to the compose file.
          # A host path like ./data or /volume1/takeout makes it a bind mount.
          # Never share a data dir with a running dev backend.
          # Security: Google sign-in is ON in this file (AUTH_ENABLED, default true here;
          # the app itself defaults to off). Put the accounts allowed to sign in in
          # backend.env, e.g. AUTH_ALLOWED_EMAILS=you@gmail.com - without it the
          # first account to sign in claims the instance. Even with sign-in, keep it on
          # the LAN or a VPN / HTTPS reverse proxy; never expose the port to the internet.
          # See the self-hosting guide for the full documentation.
          # NVIDIA GPU: use image ghcr.io/ecyshor/takepho-cuda:latest plus a GPU
          # reservation (see the guide's "NVIDIA GPU" section), or build with
          # --build-arg TORCH_VARIANT=cu132.

          services:
            app:
              image: ghcr.io/ecyshor/takepho:latest
              restart: unless-stopped
              # Grace period for SIGTERM: the app stops running work gracefully (persisted as
              # "interrupted" and resumed automatically on the next start) within ~25 s — see
              # the guide's "Updating" section — before Docker escalates to SIGKILL
              stop_grace_period: 60s
              ports:
                - "${TIMELINE_PORT:-8080}:8000"
              volumes:
                - ${TIMELINE_DATA:-timeline-data}:/data
                - ${TIMELINE_MODELS:-timeline-models}:/app/models/clip
                - ${TAKEOUT_DIR:-~/Documents/takeout}:/takeout:ro
              environment:
                APPS: ${APPS:-photos,activities,sync}
                GOOGLE_API_KEY: ${GOOGLE_API_KEY:-}
                AUTH_ENABLED: ${AUTH_ENABLED:-true}
              env_file:
                # both optional; when both exist, backend.env (next to the compose file) wins:
                # later env_file entries override earlier ones (docker/backend.env keeps
                # working for setups that run from the app repository)
                - { path: docker/backend.env, required: false }
                - { path: backend.env, required: false }

          volumes:
            timeline-data: {}
            timeline-models: {}

Both env_file entries are optional (backend.env next to the compose file, plus one other path); when both files exist, backend.env wins — later env_file entries override earlier ones.

The container listens on port 8000 (EXPOSE 8000, uvicorn on 0.0.0.0:8000) and the compose file maps it to ${TIMELINE_PORT:-8080} on the host. The image has a healthcheck: it curls http://localhost:8000/health every 30 s (30 s start period, 3 retries).

Volumes and where the Takeout folder goes

Container path Volume / variable Contents
/data ${TIMELINE_DATA:-timeline-data} Databases (common.db + one per app), thumbnails and previews, gzip indexes, uploads, Drive downloads (DRIVE_DOWNLOAD_DIR=/data/downloads)
/app/models/clip ${TIMELINE_MODELS:-timeline-models} CLIP model weights
/takeout ${TAKEOUT_DIR:-~/Documents/takeout}, mounted read-only (:ro) Your Takeout exports (TAKEOUT_SOURCE_DIR)

These paths are fixed by the image (DATA_DIR=/data, TAKEOUT_SOURCE_DIR=/takeout, DRIVE_DOWNLOAD_DIR=/data/downloads, FRONTEND_DIST=/app/frontend); do not override them in backend.env. The image also fixes the Proton settings (PROTON_DRIVE_CREDENTIALS_STORE=unsafe_file — the Proton session is kept as a 0600 auth-session.json under /data, so it survives container restarts; PROTON_DRIVE_CACHE_DIR=/data/apps/sync/proton-drive-cli; PROTON_HELPER=/usr/local/bin/takepho-proton, the bundled Proton Drive SDK helper binary); do not override those either. In the UI, use /takeout as the local-folder source.

A host path such as TIMELINE_DATA=./docker-data or TAKEOUT_DIR=/volume1/takeout turns the volume into a bind mount. Never point /data at a data dir a running dev backend is using.

Scheduled exports: ask Google to deliver new exports into the host folder you mount at /takeout (for example the NAS share /volume1/takeout), then turn on "Watch for new exports" on the Takeout page. The watcher picks up new archives in /takeout on its own.

Configuration

All backend settings go in backend.env next to the compose file — download backend.env.example from this page (https://takepho.com/self-host/backend.env.example) and copy it to backend.env to start; the file is optional — plus the compose variables (TIMELINE_PORT, TAKEOUT_DIR, TIMELINE_DATA, TIMELINE_MODELS, APPS, GOOGLE_API_KEY) in a .env next to the compose file. The backend.env options:

Variable Default Purpose
INGEST_WORKERS cpu_count - 2 Parallel ingestion workers
TRIP_TIME_GAP_HOURS 36 Photo gap that splits trip segments
HOME_RADIUS_KM 50 Home detection radius
DAY_TRIP_MAX_KM 300 Max distance from home for a day trip
CURATION_TARGET_COUNT 6 Target curated photos per trip (2-10)
RESUME_DELAY_S 15 Seconds after startup before interrupted work (imports, processing steps) is resumed automatically
GEOCODING_USER_AGENT takeout-photo Reverse geocoding user agent (only used with the online nominatim provider)
GEOCODING_PROVIDER geonames Reverse geocoding: the bundled offline GeoNames data by default (no network calls, never rate-limited); nominatim for online, finer names (~1 req/s)
STRAVA_CLIENT_ID / STRAVA_CLIENT_SECRET unset Your Strava API application (see below); can also be pasted on the Strava card in Settings

GOOGLE_API_KEY (compose variable or backend.env) is optional; it is only used for public "anyone with the link" Google Drive shares and can also be pasted in the UI.

NVIDIA GPU

The default image runs AI analysis (CLIP) on the CPU, in linux/amd64 and linux/arm64 builds. For an NVIDIA GPU the host needs the NVIDIA driver (>= 580 for CUDA 13) and the NVIDIA Container Toolkit. Two options:

  • Prebuilt CUDA image (linux/amd64 only): set image: ghcr.io/ecyshor/takepho-cuda:latest in compose.yaml and reserve the GPU:

        deploy:
                resources:
                  reservations:
                    devices:
                      - driver: nvidia
                        count: all
                        capabilities: [gpu]

The app picks the device itself (CLIP_DEVICE=auto: CUDA, then Apple MPS, then CPU; Settings shows where it runs). The CUDA image is much larger (about 8.3 GB on disk, a 3 GB download, vs about 2.1 GB / 0.5 GB for the CPU app image).

Access and security

Turn on Google sign-in for a NAS install (recommended). The app's own default is no login: anyone who can reach the port can open the app and call the API, including full-resolution photos and the connected Google / Proton accounts. The compose file therefore sets AUTH_ENABLED=true (override with AUTH_ENABLED=false in the shell or .env). To choose who may sign in, put this in backend.env:

AUTH_ENABLED=true
          AUTH_ALLOWED_EMAILS=you@gmail.com,partner@gmail.com

then docker compose up -d again.

  • AUTH_ALLOWED_EMAILS (comma-separated emails or @domain.com) restricts who may sign in; the first to sign in becomes the owner. Always set it: when empty, whoever signs in first claims the instance.
  • A middleware requires a valid sign-in session for /api/..., /docs and /redoc (401 "Sign-in required" otherwise); AUTH_SESSION_DAYS (default 30) sets the session length. Works over plain http:// on the LAN (the cookie is only Secure on HTTPS).
  • Sign-in is Google-only and needs no Google Cloud setup: it uses the OAuth relay at https://oauth.takepho.com by default (straight back for LAN / Tailscale addresses, a confirm page for others), or your own "Web application" client via AUTH_GOOGLE_CLIENT_ID / AUTH_GOOGLE_CLIENT_SECRET (its redirect URI must be <origin>/api/google/auth/callback).

Even with sign-in on, never expose the port directly to the internet. To reach it from outside, use a VPN (Tailscale, WireGuard) or an HTTPS reverse proxy (optionally with its own authentication, e.g. Caddy, nginx, Traefik plus Authelia or Pocket ID).

When running behind a reverse proxy, keep the Host header intact (proxy_set_header Host $host): the app builds OAuth callback URLs from the address the browser uses.

Google sign-in and Strava at http://nas.local:8080

Google Drive (private archives): the OAuth redirect URI is built from the address you open the app at, for example http://nas.local:8080/api/google/auth/callback.

  • The built-in client (shipped in the image) is a Google "Desktop app" client, and Google only allows loopback redirects for those. From a browser on another device the flow therefore goes through the OAuth relay at https://oauth.takepho.com (GOOGLE_RELAY_URL; the relay sends the browser straight back for loopback addresses, private / Tailscale IPs and .local / .lan / .home.arpa / .internal names, and shows a "Continue to ...?" page for anything else). From a browser on the NAS itself, open http://localhost:8080 and the built-in flow works directly. Set GOOGLE_RELAY_URL="" to turn the relay off.
  • Your own client: a "Desktop app" client (GOOGLE_OAUTH_CLIENT_ID / _SECRET, or pasted on the card) has the same loopback limit, so use it from a browser on the NAS (localhost, for example through an SSH tunnel) or via the relay. A "Web application" client can register http://nas.local:8080/api/google/auth/callback as a redirect URI and works from any browser.
  • Public Drive links ("anyone with the link") need no sign-in at all.

Strava: the callback is <origin>/api/activities/providers/strava/auth/callback. Strava only checks the callback domain, so in your Strava API application (strava.com/settings/api) set the Authorization Callback Domain to the host name you open the app at, without scheme or port: nas.local, or the LAN IP such as 192.168.1.10. Any port works. Put the Client ID and Secret in backend.env (STRAVA_CLIENT_ID / STRAVA_CLIENT_SECRET) or paste them on the Strava card in Settings. Komoot and Garmin Connect use email and password on their Settings cards; they need no redirect URIs.

Updating

docker compose pull
          docker compose up -d

Your data lives in the volumes and survives down and recreate. Only docker compose down -v deletes the data volumes.

Restarts and updates resume running work automatically

Every background job (a Takeout import, a processing step like trip detection or AI curation, an activities sync, a Proton sync, a "Start over" reset, …) survives a restart or an update:

  • On shutdown (Docker sends SIGTERM when it recreates or stops the container) the app stops its running work gracefully at the next checkpoint — within about 25 s — and records it as "interrupted" (never as "cancelled"; a cancel you trigger in the UI is never resumed automatically).
  • On the next start the app automatically resumes the interrupted work, without anyone clicking anything: the import continues over the archives that are not imported yet (already imported items are skipped), the processing steps re-run, an interrupted activities auto-sync runs right away, and an interrupted "Start over" reset finishes before any import starts. A crash-loop guard stops auto-resuming after 3 consecutive resumes that made no progress and shows an error instead (any progress resets it); the import can then be resumed manually with the "Resume import" button on the Ingestion card.

The compose files set stop_grace_period: 60s so Docker gives the container enough time for this graceful stop (the image starts uvicorn with --timeout-graceful-shutdown 5), and only then sends SIGKILL. Data lives in the volumes, so docker compose up -d after a pull, a down/up, or a container crash all continue where the work stopped.

Backups

Back up the data dir (/data, the TIMELINE_DATA volume or bind path): it holds the databases, thumbnails, previews, settings and Drive downloads. The models volume can be re-downloaded, it only holds the about 578 MB CLIP weights. The Takeout archives are not in /data; they stay in your TAKEOUT_DIR, so back that up too (or keep the Drive share active). Without reachable archives, full-resolution originals cannot be served and missing thumbnails cannot be re-rendered.

Synology, Unraid, TrueNAS

Any Docker Compose v2 host works the same way; the downloaded compose.yaml is the source of truth.

  • Synology (Container Manager, DSM 7.2+): in Projects, choose Create, then paste the contents of compose.yaml (or upload the file), put TIMELINE_PORT, TAKEOUT_DIR, TIMELINE_DATA, TIMELINE_MODELS in a .env next to the project, pick the NAS folder for TAKEOUT_DIR, then start the project.
  • Unraid: install the Compose Manager plugin, then in Docker, Compose Manager, choose New Stack, paste compose.yaml, set the same variables in the stack's .env, start the stack.
  • TrueNAS SCALE: in Apps, choose Custom App ("Install via YAML"), paste compose.yaml, set the variables and host paths, deploy.

Troubleshooting

  • Container unhealthy or restarting: docker compose ps shows the health status (the image healthcheck curls http://localhost:8000/health every 30 s); docker compose logs -f app shows the log. From the NAS itself: curl http://localhost:8080/health.
  • Empty archive list: check the mount with docker compose exec app ls /takeout, and make sure the UI's folder field says /takeout.
  • Permissions on bind mounts: the container runs as root (the image sets no USER), so files it creates in a bind-mounted /data are owned by root on the host. Prefer the named volumes (the default), or chown -R 0:0 the host dir. The /takeout mount is read-only, the app never writes there.
  • Port already in use: change TIMELINE_PORT in .env.
  • Slow import on a big library: lower INGEST_WORKERS; progress and cancel are on the Takeout page.
  • Stale UI after an update: hard-refresh the browser.

Plans and licensing

A plan is required, exactly like the desktop app. Open http://<nas-host>:8080 in any browser, go to Settings → Account, sign in with Google or Apple and buy a plan: the one-time lifetime licence (manual imports) or the yearly plan (automatic processing; includes the lifetime licence). Same plans and prices as the desktop app, tax-inclusive. The sign-in works from any browser: the app hands the sign-in off through the account service (account.takepho.com) and polls it until the session arrives, so no loopback address on the NAS is needed. The NAS counts as one of the account's 2 computers; if the limit is reached, remove another device in Settings → Account.

Importing your own Takeout then works; without a valid plan only Lite works (photos timeline limited to the 5 most recent holidays + the manual local-folder import), everything else is refused with HTTP 402. The built-in sample data ("Try with sample data") stays free, as does everything already imported (a lapsed licence caps reads the same way immediately). The app verifies a signed entitlement locally and refreshes it from the account service about every 7 days, so the server needs internet access at least once a month; offline it keeps working for up to 30 days on the cached entitlement.

The optional in-app login (AUTH_ENABLED) is off by default in Docker.

Nothing leaves your server unless you configure it: Google (Drive access), the account service for the licence sign-in/refresh above, Strava / Komoot / Garmin, the reverse geocoder for place names, and Hugging Face for the CLIP weights on the first curation run. There is no telemetry.
